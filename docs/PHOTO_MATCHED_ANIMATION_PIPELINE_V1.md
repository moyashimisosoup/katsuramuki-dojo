# APP-022｜実写感のある「動く桂むき」へのアセット／物理統合計画 v1.0

作成: 2026-10-19 JST

## 0. なぜ現行映像が見本画像に届かないのか

現行 `src/view3d/scene.js` は、大根の動的メッシュ、4頂点の刃、単純な円柱の柄、幅のある帯を画面に表示しているが、モデルは粗い。下記が根本原因。

- 刃のモデルは三角形2枚相当で、立体的な鎬、峰、刃先・柄、現実の薄刃包丁の形がない。
- 刃の上辺は固定ベクトル `lift=[0,13,11]` で作られ、**刃面の向きと刃先の位置を独立に調節できない**。これまでの `tilt` は主に幅方向の切削深さ差で、包丁面の現実の姿勢ではない。
- 大根の接触角 `CONTACT_ANGLE=Math.PI*0.33` は仮の画面設定。写真に基づいて校正した標準角ではない。
- むいた帯の形は `ribbonGuidePoint` の所定の曲線であり、重力、ねじれ、曲げ剛性、材料自体の厚みの違いを計算していない。
- 左右の手と親指の支持・回転・包丁の上下滑走がない。
- PBR材質、実物の薄片らしい光の透過、写真に対応するカメラ/環境光が未調整。
- R0の体積・半径数値テスト19件は有用だが、リアリティや実技の正しさを保証しない。

## 1. 何を「見本」にするか

- 見た目：このチャットでChatGPTが作成した横向き・両手持ちのゲーム画面案（描画表現とUIの基準）。現時点ではその画像ファイル自体を公開リポジトリへコピーせず、**このチャットのオリジナル画像との照合は未完了**。
- 動作：辻調理師専門学校の桂むき実演、京都調理師専門学校の実技動画、独立した見本写真の**実際の手の運動**。見本画像の空想的な機械式回転台、誤った刃先の形、固定角度の注釈などを「真実」として再現しない。
- 評価：写真と3Dモデルを同じカメラで重ねて、①大根の軸②包丁の切れ刃③両手の支点④帯の分離箇所⑤帯幅⑥切削時の上下ストロークについて確認する。遠近投影の1枚の画像から真の3D角度を一意に決めたと主張しない。
- デザインと実際の手技の正確性は別の承認ゲート。

## 2. 3D資産の製作方法

| 資産 | 制作・保存形式 | 動かす仕組み |
| --- | --- | --- |
| 大根 | R0から可変メッシュ＋PBR表面・断面テクスチャ。円柱は実物に近い角・中心の微細な変化を校正 | R0の材料表面データ `surfaceRadius()` |
| 包丁 | 寸法と刃先・刃面・柄の接続点を持つ自作の写実的薄刃包丁GLB（規格 `edgeStart`、`edgeEnd`、`bladeFace`、`handleAnchor`） | 刃先の位置・面の角度・上下ストロークを別の自由度として制御 |
| 左手 | リグ付きGLB（親指/指/手首、ピボットを明示） | 大根の保持、回転、指の接触位置 |
| 右手 | リグ付きGLB（握りと親指のピボット） | 包丁の柄姿勢、滑走、刃先の接触維持 |
| 桂むき帯 | 幅方向3列以上の連続メッシュ。R0から材料厚み・長さを渡す | 初期は表示用XPBD/位置拘束で重力・曲げ・ゆっくりしたねじれ |
| 背景 | 権利処理済み木目テクスチャ、まな板GLB、自然光・影 | Three.jsのライティング/PBR |

画像から自動的に3DにするAI（TRELLIS.2など）は**候補アセットの原案生成**には有効。ただし1枚の完成画像から「正しい裏側」「骨格」「包丁の刃先と物理接触」「透ける帯の動的メッシュ」までは自動復元されない。生成物はBlender等でリトポロジー、分離、手指のリギング、切削点の接続を修正する。TRELLIS.2はCUDA/GPU処理を要求するため、スマホ上・通常の無料CIでの変換を前提にしない。モデル・サービスのライセンスは使用するバージョンで確認し、有料API契約を必須にしない。

**最終ランタイムはWebブラウザのThree.js＋glTF/GLBモデル＋専用R0＋軽量柔軟体 solver。** 来訪者にBlender、3D生成AI、ローカルPythonをインストールさせない。

## 3. 正しい動きの座標系

- ワールドX: 大根の軸方向。大根本体の回転はワールドX回り。
- 刃先の接触点の法線n（ワールドY/Z断面の半径方向）、接線t、軸eは直交する。
- 3つの角度を区別する：
  1. `contactAngleRad`: 大根断面上のどの位置に接触するか。
  2. `edgeSkew`: 大根の幅方向に沿った刃先の径方向位置差。帯の上下厚さ差につながる。
  3. `bladeFaceAngleRad`: 大根の局所接平面に対する包丁面の傾き。外見と抵抗・食い込みに影響するが、現行R0はR1の切削力を計算しない。
- 4つ目の動作 `bladeStroke` は刃先が上下滑走する独立した移動。半径方向送りとの混同を禁止。
- 右手の親指・包丁の柄・刃先の接触線は同じリグ状態から更新。見た目だけ包丁を回し、R0の削れ方は別になる構図は不合格。
- 数値角度を写真から確定するまではゲーム設定として `uncalibrated` を明示し、料理の正しい標準角として紹介しない。
- 先行実装: `src/rig/knife-pose.js` では刃先、刃面、柄アンカーを独立に計算し、レンダラーなしで直交性などをテストできる。**現時点ではThree.jsシーンへの配線なし**。

## 4. 柔軟物理と描画の結合

1. R0 `cutSweep` が単位時間に剥離した範囲・幅方向の厚さ・体積を決定する。
2. 新しくむけた帯の頂点列を、切削線に連続した同一シートとして生成する（幅方向3〜5列×長さ方向のセグメント）。
3. 帯の出始めは大根との切削接点に固定する。帯が伸びると節点が増え、重力により落ち、幅方向曲げ・ねじれ・伸長拘束で変形する。
4. 初期はPBD/XPBDの軽量CPU計算を候補にし、**素材物性は仮値**。長い帯・低スペックのiPhoneでは節点数を上限管理し、軽量シート表現へ自動縮退。
5. 表示と数理を分離。切削長・厚みの値はR0からのみ取得し、描画FPSで増やさない。
6. 帯の透過はThree.jsのPBR、可能ならMeshPhysicalMaterialのclearcoatや透過を試験。厚みを「透明度だけ」で誤表現しない。iOS Safariで透過のレンダリング負荷を検査する。

## 5. 画像→3D化の具体的なゲート

### V-A 正確な静止姿勢
実演の1シーンを選び、手・大根・刃の位置、包丁面、帯の出口が**3Dの静止画として成立**する。見本画像の光・素材と比較する。**静止姿勢が不合格なら物理で動かさない。**

### V-B 5秒の基礎モーション
大根回転、右手の上下滑走、包丁の刃先の接触、帯の剥離が同じ時間軸で動く。指が道具をすり抜けない。

### V-C 切削コアとの同期
R0体積保存、帯幅、刃の接触点の一致を保持。大根が細るだけでなく、帯の入口が刃に接していることを検査。

### V-D 柔軟体
帯の曲がり、垂れ、ねじれ、切れたときの離脱を導入。破断が不正確な期間は意図的な「破れ演出」として表示しない。

### V-E ブラウザ受入
PCブラウザとiPhone Safariで3D品質、操作遅延、描画FPS、メモリ、帯のすり抜け、手のめり込みを確認。達成した描画品質のみ本番へ反映。
